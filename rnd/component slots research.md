## Исследование реализации слотов

Я изучил типажи hypertext (Renderable, Raw, Lazy, и impl-ы в renderable/impls.rs). Несколько фактов оттуда определяют, что вообще возможно, поэтому сначала зафиксирую их — на них опираются все варианты ниже:

  - Renderable<C> имеет единственный метод render_to(&self, &mut Buffer<C>) → типаж object-safe.
  - В impls.rs есть impl<T: Renderable<C> + ?Sized> Renderable<C> for Box<T> (через render_via_deref!) → Box<dyn Renderable> сам реализует Renderable «из коробки».
  - impl<T: Renderable<C>> Renderable<C> for Option<T> → пустой слот (None) рендерится в ничто бесплатно. Так уже работает children: Option<R>.
  - RenderableExt::memoize() → Raw<String>: любой renderable можно заранее отрендерить в строку и стереть его тип до одного конкретного типа.
  - Макрос #[prop(convert)] уже умеет подменять generic-параметр для каждого поля независимо (replace_generic_param), а #[prop(into)] генерирует сеттер вида impl Into<T>.

  Ниже — варианты от «нулевой стоимости, но многословный тип» до «максимально похоже на slot, но инвазивно».

  ---
  Вариант 1. Именованные слоты как renderable-атрибуты через generic-параметры (zero-cost)
  
  Каждый слот — отдельный параметр типа с дефолтом (), как нынешний children:

  #[derive(Default, AsRef, AsMut, Props)]
  #[props(builder)]
  pub struct Input<Label = (), Start = (), End = (), Hint = ()>
  where Label: Renderable, Start: Renderable, End: Renderable, Hint: Renderable {
      #[prop(convert)] pub label: Option<Label>,
      #[prop(convert)] pub start: Option<Start>,
      #[prop(convert)] pub end:   Option<End>,
      #[prop(convert)] pub hint:  Option<Hint>,
      // ... обычные поля ...
  }

  Вызов: <Input start=(rsx!{ <span class="icon">… </span> }) label=(rsx!{ "Email" }) />; в render_to — просто (self.start), (self.label) в нужных местах.

  - Плюсы: ноль аллокаций и динамической диспетчеризации, ленивый рендер, имена слотов проверяются компилятором. Менять ничего не нужно — макрос уже это поддерживает.
  - Минусы: «взрыв» сигнатуры типа (Input<A, B, C, D>); хранить/возвращать такой Input вне rsx неудобно; добавление нового слота меняет арность типа.

  Вариант 2. Стирание типа через Box<dyn Renderable> в каждом поле

  pub struct Input {
      pub label: Option<Box<dyn Renderable>>,
      pub start: Option<Box<dyn Renderable>>,
      // ...
  }
  // сеттер: self.start = Some(Box::new(content));
  // render: @if let Some(s) = &self.start { (s) }   // работает, см. impl для Box и &T

  - Плюсы: никаких generic-ов в типе, ленивый рендер, имена-поля проверяются компилятором, легко добавлять слоты.
  - Минусы: heap-аллокация + dyn-вызов на слот; контент должен быть 'static (иначе нужен Box<dyn Renderable + 'a> и лайфтайм-параметр у структуры); #[prop(into)] сам не выполнит unsize-коэрцию, поэтому нужен
  ручной сеттер (см. Вариант 2-бис, который это чинит).

  Вариант 2-бис (рекомендуемый). Ньютайп Slot + существующий #[prop(into)]

  Это «Вариант 2», но без правки макроса — задействуем уже имеющийся режим into:

  pub struct Slot(Box<dyn Renderable>);          // НЕ impl Renderable (чтобы не конфликтовать с From<T> for T)
  impl<R: Renderable + 'static> From<R> for Slot {
      fn from(r: R) -> Self { Self(Box::new(r)) }
  }
  impl Slot { fn render_to(&self, b: &mut Buffer) { self.0.render_to(b) } }

  #[derive(Default, AsRef, AsMut, Props)]
  #[props(builder)]
  pub struct Input {
      #[prop(into)] pub start: Option<Slot>,     // макрос сгенерит fn start(impl Into<Slot>)
      #[prop(into)] pub label: Option<Slot>,
      // ...
  }

  Вызов получается ровно как с обычным атрибутом: <Input start=(rsx!{ … }) /> или .start(rsx!{ … }).

  - Плюсы: минимум нового кода (один ньютайп + blanket-From), никаких изменений в макросе, компиле-тайм имена слотов, единый плоский тип Input. Ровно повторяет привычный для проекта стиль #[prop(into)] 
  Option<Cow>.
  - Минусы: те же аллокация/диспетчеризация и 'static, что у Варианта 2. Нюанс: чтобы blanket-From<R> не столкнулся с рефлексивным From<T> for T, Slot не должен сам реализовывать Renderable (рендерить —
  отдельным методом).

  Вариант 3. Заранее отрендеренные слоты через Raw<String> (.memoize())

  pub struct Input { pub label: Option<Raw<String>>, /* ... */ }
  // сеттер: self.label = Some(content.memoize());

  - Плюсы: единый конкретный тип, без generic-ов, без dyn-вызова при рендере родителя (копия байтов), владеет своими данными — никаких лайфтаймов. Самый простой по типам.
  - Минусы: жадный рендер и аллокация в момент сборки, даже если слот в итоге не выводится; теряется ленивость; контент рендерится вне буфера/контекста родителя.

  Вариант 4. Динамическая карта слотов (ближе всего к slot="name" по модели, но stringly-typed)

  pub struct Input { slots: HashMap<&'static str, Box<dyn Renderable>> }
  // .slot("start", rsx!{ … })  →  в render: self.slots.get("start")

  - Плюсы: ментальная модель 1:1 с web-компонентным slot="name"; новые слоты без изменения структуры; одно поле.
  - Минусы: имена слотов не проверяются компилятором (опечатка → слот молча проигнорирован), хеш/аллокации, dyn-вызовы.

  Вариант 5. Буквальный синтаксис слотов в теле компонента (идеальная эргономика, но инвазивно)

  Хотелось бы писать как в HTML:
  <Input>
      <Slot name="start"> … </Slot>
      <Slot name="label"> "Email" </Slot>
  </Input>
  Проблема: rsx! «схлопывает» детей в один Renderable, и родитель не может разобрать их на слоты. Чтобы это заработало, детей надо представлять структурой (например, children: Vec<NamedSlot { name: 
  Option<&'static str>, body: Box<dyn Renderable> }>) и иметь хелпер/макрос, который собирает этот Vec из тела.
  
  - Плюсы: максимально близко к web-компонентным слотам, единая точка входа (тело компонента).
  - Минусы: самый инвазивный — требует менять способ передачи детей (или отдельный slots!-хелпер) и расходится с моделью детей в hypertext. Это «конечная цель по эргономике», а не «базовое» решение.

  ├──────────────────────────┼──────────────┼──────────────┼───────────┼─────────────────┤
  │ 2/2-бис. Box<dyn> / Slot │ alloc + dyn  │ compile-time │ 'static*  │ нет (2-бис)     │
  ├──────────────────────────┼──────────────┼──────────────┼───────────┼─────────────────┤
  │ 3. Raw<String>           │ жадный alloc │ compile-time │ нет       │ нет             │
  ├──────────────────────────┼──────────────┼──────────────┼───────────┼─────────────────┤
  │ 4. Карта                 │ alloc + dyn  │ runtime      │ 'static*  │ нет             │
  ├──────────────────────────┼──────────────┼──────────────┼───────────┼─────────────────┤
  │ 5. Синтаксис в теле      │ alloc + dyn  │ runtime      │ 'static*  │ да, существенно │
  └──────────────────────────┴──────────────┴──────────────┴───────────┴─────────────────┘

  * можно снять, добавив лайфтайм-параметр структуре.

  - Если важнее всего эргономика и минимум нового кода — Вариант 2-бис (Slot + #[prop(into)]): даёт <Input start=(rsx!{…}) />, проверяемые имена слотов, плоский тип, и встраивается в существующий
  #[derive(Props)] без его изменения. По соотношению «польза/риск» — лучший.
  - Если критична нулевая стоимость (горячий путь, много инстансов) — Вариант 1; цена — многословный generic-тип.
  - Вариант 4 — только если нужно динамически набирать произвольные слоты и не жалко потерять проверку имён.
  - Вариант 5 держать как ориентир «идеального» API, если позже захочется буквального slot-синтаксиса.

  Можно и комбинировать: оставить дефолтный слот телом (children: Option<R>, как сейчас) и добавить именованные слоты по схеме 2-бис — это ближе всего к web-компонентам (один безымянный + N именованных).

Чтобы предложения по Варианту 5 были обоснованными, мне нужно точно понять, как rsx! раскрывает детей компонента и во что они превращаются. Изучу исходники макроса hypertext-macros.

Изучил раскрытие компонентов в hypertext-macros (html/component.rs). Это меняет картину по Варианту 5, поэтому сначала — ключевая находка, а затем реалистичные пути.

  Как макрос на самом деле раскрывает тело компонента

  <Input attr=val> …дети… </Input> всегда превращается в (component.rs:36-59):

  Input::builder()
      .attr(val)
      .children(::hypertext::Lazy::dangerously_create(
          |__hypertext_buffer: &mut Buffer| { /* каждый ребёнок пишется в буфер по порядку */ }
      ))
      .build()

  Отсюда три жёстких факта:

  1. Все дети сплавляются в один непрозрачный Lazy-замыкание, которое пишет HTML прямо в буфер. Родитель получает не список узлов, а одну функцию «отрендерь всё сюда».
  2. Метод всегда буквально .children(...); имя и форма зафиксированы макросом.
  3. Значение атрибута может быть Literal | Ident | (expr) → слот-как-атрибут выглядит как <Input start=(rsx!{…})>.

  Вывод: «честный» Вариант 5, где родитель переставляет <Slot name="start"> из тела в произвольное место разметки, невозможен на стоковом hypertext без модификации его макроса — к моменту, когда родитель видит
  детей, они уже сведены к одному буфер-писателю и не поддаются интроспекции. Менять внешний крейт нельзя, значит остаются обходные стратегии. Их три рабочих + одна «идеальная, но требует форка».

  Предложение A. CSS-проекция (самое простое, настоящий body-синтаксис)
  
  Slot — наш компонент, который рендерит обёртку с маркером слота, а позиционирование делает CSS:

  // <Input><Slot name="start">(icon)</Slot>"text"<Slot name="end">…</Slot></Input>
  // Slot::render_to → <span class="wa-slot" data-slot="start">…</span>
  Родитель один раз вставляет (self.children) внутрь flex/grid-контейнера, а CSS раскладывает:
  .text-field { display: flex; }
  .text-field [data-slot="start"] { order: -1; }
  .text-field [data-slot="end"]   { order:  1; }
  
  - Плюсы: буквальный синтаксис в теле, ноль изменений в макросе и рантайме, никакой диспетчеризации/парсинга.
  - Минусы/границы: переставляет только визуально и только среди сиблингов одного контекста форматирования. Слоты на разных уровнях вложенности (например, start/end внутри .text-field, а label/hint — снаружи)
  одной точкой вставки (self.children) не накормить. DOM-порядок = порядок в исходнике (нюансы доступности/таб-порядка).
  - Годится для: input start/end-иконок, кнопок с префиксом/суффиксом — там, где слоты лежат в одном ряду.

  Предложение B. Слот-«сток» через thread-local (настоящая проекция, рекомендуемое)

  Идея: Slot при рендере не пишет в буфер родителя, а кладёт (имя, отрендеренный_контент) в thread-local стек кадров; родитель сам решает, куда это вставить.

  thread_local! { static SINK: RefCell<Vec<HashMap<&'static str, Raw<String>>>> = …; }

  // Slot::render_to(&self, buffer):
  //   если есть активный кадр → отрендерить своих детей в строку,
  //   положить в кадр по self.name, в buffer не писать НИЧЕГО;
  //   иначе (нет родителя) → отрендерить детей инлайн (грациозный фолбэк).

  // Input::render_to(&self, buffer):
  //   SINK.push_frame();
  //   let mut scratch = Buffer::new();
  //   self.children.render_to(&mut scratch);     // Slot-дети ушли в кадр, остальное — в scratch
  //   let frame = SINK.pop_frame();
  //   let default = Raw::dangerously_create(scratch.into_inner());
  //   // дальше свободно раскладываем:
  //   //  frame["label"], <div text-field> frame["start"] <input> frame["end"] </div>, default, frame["hint"]

  Все нужные кирпичи в API есть: Buffer::new()/push/into_inner, Raw::dangerously_create (используется в memoize).

  - Плюсы: настоящая проекция в любые позиции и на разные уровни вложенности; буквальный body-синтаксис; имена слотов известны родителю; реэмит через Raw безопасен (контент уже экранирован). На WASM
  (однопоточно) thread-local идеален.
  - Минусы: глобальное скрытое состояние; нужен стек кадров для вложенных слот-компонентов (учтено через push/pop); каждый слот = одна аллокация строки + проход; Slot вне родителя требует фолбэка. Чуть «магии»,
  но инкапсулируется в один модуль.

  Предложение C. Маркеры + render-then-split (альтернатива B без thread-local)

  Slot оборачивает контент однозначными границами, родитель рендерит детей в строку и режет по маркерам:

  // Slot::render_to → <!--wa-slot:start-->…контент…<!--/wa-slot:start-->
  // Input::render_to: s = self.children.to_buffer().into_inner();
  //   вырезать сегменты между маркерами по известным именам, остаток = default-слот,
  //   реэмитить нужные куски через Raw в нужных местах.

  - Плюсы: без глобального состояния; та же сила проекции, что у B.
  - Минусы: парсинг собственного вывода (резка строки), хрупкость при теоретическом совпадении маркера в контенте (лечится nonce/<template data-slot>); маркеры-комментарии остаются в выводе, если не вычищать;
  двойная работа (рендер → парс → реэмит).

  Предложение D. Расширить макрос hypertext (единственный «чистый» структурный путь — вне текущего скоупа)

  Научить component.rs распознавать детей-<Slot name="x"> и маршрутизировать их в отдельные builder-вызовы (.slot_x(...)), а не сваливать в один Lazy. Тогда дети станут структурой, и слоты будут zero-cost и
  проверяемы компилятором — как настоящие slot-ы.

  - Плюсы: идеальная эргономика и стоимость, статическая проверка имён.
  - Минусы: требует форка/PR в hypertext (внешняя зависимость) — то есть выход за рамки «ничего не меняем у себя». Стоит держать как ориентир/возможный upstream-вклад.

  - Если нужен настоящий Вариант 5 уже сейчас, без форка — Предложение B (thread-local sink): даёт буквальный <Input><Slot name="start">…</Slot></Input> с проекцией в любые позиции, вся «магия» прячется в один
  модуль slot. Это лучший баланс «эргономика/реализуемость».
  - C — если хочется избежать глобального состояния ценой резки строк.
  - Прагматичный гибрид: слоты одного уровня (start/end в .text-field) сделать через A (CSS-order), а разноуровневые label/hint оставить обычными атрибутами (#[prop(into)], как сейчас). Минимум сложности,
  покрывает реальные кейсы input/button.
  - D — как цель для upstream, если позже понадобится строгий zero-cost slot-синтаксис на уровне самого hypertext.

  Во всех вариантах строительный блок один и тот же — собственный компонент Slot (<Slot name="…">), который hypertext спокойно принимает как обычный PascalCase-компонент; различается лишь то, что
  Slot::render_to делает (пишет с маркером / кладёт в sink / просто оборачивает для CSS).
