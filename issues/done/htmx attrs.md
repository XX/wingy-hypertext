Необходимо реализовать поддержку HTMX-атрибутов для компонентов с минимумом бойлерплейта для пользователя. Компонент может содержать поле `htmx`, тип которого возможно реализовать по подобию существующего `CommonAttrs` или `Link`, с той лишь разницей, чтобы он содержал в себе коллекцию атрибутов, а не имел по полю на каждый возможный атрибут. Список поддерживаемых атрибутов есть в именах констант у трейта `hypertext::prelude::HtmxAttributes`, описывающий возможные HTMX-атрибуты стандартных HTML-элементов. Новый тип, позволяющий задавать HTMX-атрибуты пользовательским компонентам будет иметь трейт, билдер-методы и методы доступа к каждому атрибуту, который может возвращать опциональное значение в зависимости от того, указан был этот атрибут или нет.

Это только первая часть задачи - поддержать задание HTMX-атрибутов для компонентов. Вторая часть - это реализовать вспомогательный код для менее трудоёмкой установки внутри компонета полученных HTMX-атрибутов в элементы в `rsx`-разметке. Чтобы пользователю не приходилось для всякого компонета перечислать руками в коде все возможные HTMX-атрибуты, предлагается скрыть данное перечисление за процедурным макросом - атрибутом `#[htmx_attrs]`, который должен навешиваться на макрос `rsx!`:  
```rust
#[htmx_attrs]
rsx! {
    <button
        id=[id]
        class=[&class_line]
        style=[&style_line]
        htmx=[self.htmx]
    >
        (self.children)
    </button>
}
```
И разворачиваться в подобное:
```rust
rsx! {
    <button
        id=[id]
        class=[&class_line]
        style=[&style_line]
        hx_get=[self.htmx.hx_get()]
        hx_post=[self.htmx.hx_post()]
        //... и так далее
    >
        (self.children)
    </button>
}
```
Новый атрибутный процедурный макрос должен быть добавлен в крейт `crates/macros`. Если знаешь более элегантное решение - предложи на рассмотрение его.

Добавь поддержку HTMX-атрибутов в компонент `Button`.

Готово. Все проверки зелёные: cargo +nightly fmt --check, clippy --all-targets -D warnings, 24 теста проходят (включая новый button::htmx), сборка WASM-клиента — ок.

  Что реализовано

  Часть 1 — тип Htmx (crates/lib/src/htmx.rs), без процедурного макроса, как вы просили. Вместо htmx_type! использован декларативный macro_rules! htmx_attrs!, которому один раз передаётся список атрибутов
  (hx_get => "hx-get", …). Он порождает:
  - Htmx — хранит атрибуты как коллекцию Vec<(HtmxAttr, Cow)> (не поле на атрибут), set_attr заменяет существующее значение;
  - инхерентные аксессоры Htmx::hx_get(&self) -> Option<&str> и т.д. (их зовёт сгенерированная разметка — без импортов);
  - трейт HtmxSetters с чейнящимися билдер-методами hx_get(self, impl Into<Cow>) -> Self, blanket-impl для T: AsMut<Htmx> — то есть компонент с полем #[as_mut] htmx: Htmx автоматически получает
  .hx_get(..).hx_target(..).

  Исключены hx-on (namespaced) и устаревший hx-vars.

  Часть 2 — макрос htmx_rsx! (crates/macros/src/htmx.rs, зарегистрирован в lib.rs). Так как буквальная #[htmx_attrs] на выражении не компилируется на stable, сделана функциональная обёртка: находит токены
  htmx=[EXPR] (рекурсивно по группам), заменяет на hx-get=[(EXPR).hx_get()] …  для всех атрибутов и форвардит в ::hypertext::rsx!.

  Часть 3 — Button: добавлено поле #[as_ref] #[as_mut] pub htmx: Htmx, render_to переведён с rsx! на htmx_rsx!, htmx=[self.htmx] добавлен в обе ветки (<a> и <button>), в импорты добавлен HtmxAttributes (нужен
  rsx для валидации hx-*). Использование: Button::builder().hx_get("/x").hx_target("#y") или <Button hx_get="/x" hx_target="#y">.

  Плюс тесты button::htmx и заметка в CLAUDE.md.

  На что обратить внимание

  - Дублирование списка атрибутов в двух местах (htmx_attrs! в lib и HTMX_ATTRS в macros). Это вынужденно: proc-macro-крейт не может экспортировать обычные const, а Часть 1 теперь не генерируется из общего
  источника. Расхождение почти всегда ловится компилятором (макрос зовёт несуществующий аксессор). Пометил комментариями «держать в синхроне».
  - Порядок рендеринга htmx-атрибутов — канонический (по списку), а не по порядку установки.
  - Я выбрал macro_rules! как «не процедурный» способ убрать ~76 повторяющихся методов. Если вы имели в виду полностью ручной код типа Htmx без всякого макроса — скажите, разверну вручную.
